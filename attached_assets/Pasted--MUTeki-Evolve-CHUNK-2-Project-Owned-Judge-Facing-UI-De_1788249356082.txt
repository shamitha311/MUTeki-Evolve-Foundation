# MUTeki-Evolve — CHUNK 2

## Project-Owned Judge-Facing UI / Demo Console

You are implementing **Chunk 2** of the Muteki-Evolve hackathon project.

Chunk 1 has already established the project foundation and application contracts.

Your job is now to build the **project-owned frontend/dashboard** that will eventually visualize the autonomous security investigation and strategy-evolution loop.

This UI must work **WITHOUT a real Muteki installation**.

The first implementation must use deterministic mock/replay data.

Later developers will connect the real backend.

Do NOT redesign the architecture.

---

# 0. STOP CONDITIONS — READ FIRST

Before writing UI code, know when to halt and report instead of guessing.

**STOP and write a clear note in `docs/UI_CONTRACT.md` (do not guess, do not invent, do not silently work around) if:**

1. **Chunk 1's contract docs don't exist at all** (`docs/INTEGRATION_CONTRACT.md` missing, or `app/models/` missing/empty). Don't recreate them from scratch or invent your own version — report that Chunk 1 needs to finish first and stop.
2. **Chunk 1's contracts exist but are incomplete or marked "Not yet verified"** for something Chunk 2 needs (e.g., the real event shape, the adapter's return type). This is not a hard stop — build against what does exist, use the project-owned models as-is even if partial, and note explicitly in `docs/UI_CONTRACT.md` which parts of the UI are built against provisional/unverified contracts.
3. **The real project-owned model field names differ from the illustrative examples in this plan** (e.g., Sections 11, 17, 19 show `progress_score`, `solved`, `getCurrentStrategy()`, etc. as examples). The real model from `app/models/` always wins. Do not rename the real model to match this document, and do not silently maintain two parallel shapes — adapt the UI to the actual contract and note the difference if it's non-trivial.
4. **No frontend framework/stack has been established by Chunk 1** (or an existing Replit project already has one that isn't React). Don't assume React because the layout language in Section 2 uses component-style names. Inspect `app/ui/` and the existing project setup first; match what's there. If genuinely nothing exists yet, choosing React (or whatever the existing broader stack implies) is reasonable — just state the choice explicitly in `docs/UI_CONTRACT.md` rather than assuming it silently.

As in Chunk 1: none of these mean abandon the chunk. They mean document the real situation, make the smallest safe decision needed to keep moving, and flag it clearly.

# 2. UI ARCHITECTURE RULE

The UI is a thin presentation layer.

The architecture should be:

Project-owned Application Contracts
↓
UI Data Adapter / View Model
↓
UI Components
↓
Judge-facing Dashboard

The UI must NOT directly import:

* Muteki worker classes
* Muteki coordinator
* Muteki blackboard internals
* Muteki event objects
* MTASA internal classes
* MTASA frontend components

The UI must consume normalized application-level data.

Note on stack: this document sometimes refers to "React/UI Components" as shorthand. That is not a mandate — see STOP CONDITION 4 (Section 0). Use whatever frontend approach the existing project has already established; only choose a new one if nothing exists yet, and state that choice in `docs/UI_CONTRACT.md`.

# 13. TARGET HANDLING

The UI may DISPLAY the trusted SandboxTarget.

The UI must NOT allow arbitrary target creation or target override.

Do not create:

* URL target input
* arbitrary host input
* runtime_reference editor
* "change target" field
* command input

The UI should treat the target as trusted application state.

If target selection is eventually needed, it must be implemented through a trusted application-level mechanism, not free-form generated input.

For this chunk, displaying the current registered target is sufficient.
