7. STRATEGY EVOLUTION BEHAVIOR
==================================================

The engine must NOT simply generate random different text.

Strategy changes must have a reason.

Examples:

If previous strategy focused on reconnaissance and produced useful surface information:

Next strategy may move toward:

- authentication
- authorization
- input validation
- deeper surface analysis

If previous strategy produced strong evidence around authentication:

Next strategy should focus more deeply on authentication-related investigation.

If a direction repeatedly fails:

The next strategy should reduce emphasis on that direction and explore another reasonable direction.

If the system is making progress:

Continue or deepen successful investigation directions.

If progress is weak:

Change investigation direction.

If progress stagnates:

Trigger Teacher/Reviewer behavior.

11. STAGNATION DETECTION
==================================================

Implement stagnation handling.

The Strategy Engine should detect situations such as:

- repeated low scores
- repeated identical outcomes
- repeated strategies
- no meaningful new evidence
- same direction repeatedly failing

Do NOT make stagnation detection dependent on an arbitrary large number of iterations.

Use a small configurable threshold.

Example:

If the last 2–3 iterations show no meaningful progress:

mark:

stagnated = true

Then the Teacher/Reviewer should recommend diversification.

==================================================
12. STRATEGY DIVERSIFICATION
==================================================

When stagnation occurs:

DO NOT generate random nonsense.

Instead:

1. Summarize failed directions.
2. Identify explored directions.
3. Identify unexplored reasonable directions from the available objective/context.
4. Produce a revised strategy emphasizing an unexplored direction.
5. Preserve the overall objective.
6. Preserve sandbox constraints.
7. Increment revision.
8. Set parent_revision to the previous strategy revision.

Example:

Previous:

Strategy #2
Focus:
authentication

Result:
no meaningful progress

Reviewer:

Authentication investigation has not produced new evidence.

Next:

Strategy #3
Focus:
authorization and input validation

This demonstrates strategic diversification.

==================================================
13. DEDUPLICATION
==================================================

Implement strategy deduplication.

The engine must prevent nearly identical strategies from being generated repeatedly.

Strategies should be compared using normalized semantic fields such as:

- objective
- priorities
- constraints
- meaningful context

Do not rely only on object identity.

Do not require sophisticated embeddings.

A deterministic normalization/hash/fingerprint approach is sufficient.

If a candidate strategy is effectively identical to a recent strategy:

generate an alternative.

If an alternative cannot be generated:

return a controlled result indicating that strategy generation requires diversification.

Do NOT silently return the exact same strategy indefinitely.

==================================================
14. REVISION TRACKING
==================================================

Every strategy must have:

revision

parent_revision

Rules:

Initial strategy:

revision = 1
parent_revision = null

Next strategy:

revision = previous revision + 1
parent_revision = previous revision

Example:

Strategy #1
parent = null

Strategy #2
parent = 1

Strategy #3
parent = 2

Do not reset revision numbers during normal operation.
